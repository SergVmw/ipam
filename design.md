# IPAM-lite — учёт IP-адресов. Дизайн (v0.3, теория)

Дата: 2026-08-18. Статус: lite-контур (обсуждено сокращение scope).

## 0. Scope — «лёгкий» вариант

**Полноценный IPAM избыточен.** Реально нужно: **скан IP + ручной ввод/изменение IP**
+ отображение + график. Всё остальное — не в MVP.

**Масштаб:** ~100 сетей, медленно растут. MAC/L2 — пока не рассматривается; если
понадобится — **один агент** с доступом ко всем нужным сетям (≤10), отложeno.

**Входит в MVP:**
1. Управление **сетями (подсетями)** — ~100 шт., медленно растут. CRUD, поиск, фильтры.
2. Управление **VLAN** — VID, имя, цвет, привязка сетей.
3. **Визуальное отображение** — IP-грид /24 (16×16), цвет = статус.
4. **Скан IP** — ручной (кнопка) + по расписанию. `fping` + PTR (авто-hostname).
5. **Ручной ввод/изменение IP** — зарезервировать, owner, заметка, override hostname.
6. **График заполняемости** — по времени + текущий + топ подсетей.

**Явно НЕ входит (lite):**
- Устройства, топология, LLDP, порты, RANCID, теги, сложные отчёты.
- LDAP/SSO и продвинутый RBAC — простая аутентификация (несколько пользователей, 3 роли).
- **MAC / L2** — отложено до явной необходимости (см. §8).

## 1. Архитектура (упрощённая)

Один сервис: **FastAPI** (API + UI + встроенный планировщик сканов APScheduler) + **PostgreSQL**.
Сканер — фоновый поток внутри приложения. Если сканы станут тяжёлыми — вынесём в отдельный
воркер, но на ~100 подсетей это не нужно (fping-свип всего парка ~25–50 c).

```
[Браузер] --> [ app: FastAPI + React UI + scheduler ] --> [ PostgreSQL ]
                     |
                     +--> fping      (ICMP-свип, живые IP)
                     +--> dnspython  (PTR -> hostname)
```

Развёртывание: `docker-compose` = `db` + `app` (2 контейнера).

Frontend: React + TS + ECharts. Если хочется ещё легче — вариант на HTMX (сервер-рендер),
но для грида + графиков React удобнее.

## 2. Модель данных (PostgreSQL)

```sql
create extension if not exists btree_gist;

create table vlan (
  id    int generated always as identity primary key,
  vid   int not null unique check (vid between 1 and 4094),
  name  text not null unique,
  color text,
  descr text
);

create table subnet (
  id              int generated always as identity primary key,
  cidr            cidr not null unique,
  ip_range        iprange generated always as (inet_range(cidr)) stored,
  name            text not null,
  vlan_id         int references vlan(id) on delete set null,
  gateway         inet,
  dhcp_start      inet,
  dhcp_end        inet,
  scan_enabled    boolean not null default false,
  scan_interval_s int check (scan_interval_s is null or scan_interval_s >= 60),
  descr           text,
  exclude using gist (ip_range with &&)   -- запрет пересечения подсетей
);

create type ip_state as enum ('free','used','reserved','offline');

create table ip (
  ip         inet primary key,
  subnet_id  int not null references subnet(id) on delete cascade,
  state      ip_state not null default 'free',
  mac        macaddr8,          -- отложено: пусто, пополним если появится агент (<=10 сетей)
  hostname   text,
  hostname_manual boolean not null default false,  -- true = ручное, не затираем PTR
  owner      text,
  note       text,
  is_gateway boolean not null default false,
  in_dhcp    boolean not null default false,
  first_seen timestamptz,
  last_seen  timestamptz
);
create index on ip (subnet_id, state);

create table scan_run (
  id          bigint generated always as identity primary key,
  subnet_id   int not null references subnet(id) on delete cascade,
  started_at  timestamptz not null default now(),
  finished_at timestamptz,
  alive int, new_ips int, freed_ips int
);

create table ip_event (
  id        bigint generated always as identity primary key,
  ip        inet,
  subnet_id int references subnet(id) on delete cascade,
  type      text not null,   -- ip_seen | ip_freed | hostname_changed | reserved_alive
  detail    jsonb,
  at        timestamptz not null default now()
);
create index on ip_event (subnet_id, at desc);

create table usage_snapshot (
  subnet_id int not null references subnet(id) on delete cascade,
  at        timestamptz not null default now(),
  total int, used int, free int, reserved int,
  primary key (subnet_id, at)
);
```

- Таблица IP **полная**: при создании подсети вставляем все адреса разом
  (`insert ... select set_ip(network(cidr)::bigint + g) from generate_series(...)`).
  100 подсетей * ~254 = ~25k строк — для Postgres ничтожно.
- `hostname_manual` — защищает ручной ввод hostname от затирания авто-PTR при следующем скане.
- `mac` — есть в модели, но пока не заполняется (модуль L2 отложен).

## 3. Сканер

Встроенный планировщик (APScheduler): каждая подсеть со своим интервалом, глобальный
параллелизм (asyncio, 8 подсетей), джиттер, опциональное «окно сканирования».

Пайплайн на подсеть:
1. Пропускаем network/broadcast, gateway и DHCP-диапазон помечаем отдельно.
2. **Ping-свип:** `fping -a -g <cidr> -t 500 -G 500` (живые IP). Fallback при ICMP-блоке —
   TCP на 22/80/443/3389.
3. **DNS (PTR):** для каждого newly-alive IP — reverse lookup через dnspython, асинхронно,
   таймаут 2 с, свои name-servers (внутренние зоны). **hostname подставляется автоматически.**
4. **Diff с БД:**
   - новый живой IP → `used`, `first_seen`, событие `ip_seen`;
   - PTR исчез → оставляем последний known hostname + `hostname_changed`;
   - **ручной hostname (`hostname_manual=1`) не затирается**;
   - был `used`, теперь мёртв → `offline`/`free` после N промахов (2, защита от флэппинга);
   - **`reserved_alive`** — зарезервированный IP жив (виден без MAC).
5. Записываем `scan_run` + `usage_snapshot`.

MAC-конфликты — **отложены** (нужен MAC). Остальное детектится и без него.

Опционально: алерт (Telegram/webhook) на новые IP / `reserved_alive` / заполнение > 90%.

## 4. Визуализация

**Страница подсети — IP-грид:**
- /24 → 256 ячеек (16×16), CSS Grid. Цвета: свободно (светлый) / занято (зелёный) /
  резерв (жёлтый) / gateway (синий) / DHCP (штриховка) / offline (серый).
- Hover: tooltip (IP, hostname, owner, last_seen). Клик → карточка IP + действия
  (назначить, снять, зарезервировать, заметка, override hostname).
- Крупные подсети: блоки /24 → клик → детализация; > 1024 ячеек — Canvas.

**Обзор сети (главная):** список VLAN → плитки подсетей (имя, CIDR, штрих заполненности,
mini-heatmap, статус скана). Клик → страница подсети.

## 5. Ручной ввод/изменение IP

- Ввести IP вручную (даже если скан его не видел) → создать запись.
- Зарезервировать / снять резерв; owner; заметка; **override hostname** (ставит `hostname_manual`).
- Освободить IP. Всё пишется в `ip` + `audit` (кто/когда).

## 6. График заполняемости (ECharts)

Источник: `usage_snapshot` (на каждый скан + периодический снимок, агрегация до дня).
1. **Линия** — % занятости подсети (или сети) по времени: 7/30/90 дн.
2. **Донат** — сейчас: free / used / reserved / dhcp / gateway.
3. **Бары** — топ подсетей по заполненности.
4. **Прогноз** — линейная экстраполяция: «/24 закончится к <дата>».

## 7. API (REST)

```
GET/POST/PUT/DELETE /api/vlans
GET/POST/PUT/DELETE /api/subnets
GET  /api/subnets/{id}/ips?state=&q=&page=
PUT  /api/ips/{ip}                 # ручное: owner/note/reserved/hostname
POST /api/subnets/{id}/scan        # ручной запуск
GET  /api/subnets/{id}/usage?days=30
GET  /api/events?subnet=&from=&to=
```
Аутентификация: **несколько пользователей**, JWT, роли `admin` / `operator` (скан + правка IP) /
`viewer` (чтение). Все изменения IP/сетей/VLAN пишутся в `audit_log` (кто, что, когда, до/после).

## 8. MAC / агент (реализован: cron-скрипт, принудительный опрос, конфиг-синхронизация)

Агент = **один POSIX-sh скрипт** (`agent/ipam_agent.sh`, без Python, без зависимостей
кроме curl/nmap/iproute2/cron) + cron на машине в VLAN.

### Размещение
Один агент с L2-доступом к нужным VLAN (≤10): ВМ с саб-интерфейсами, контейнер с
macvlan, либо бокс с хелпер-адресом в каждом VLAN на ядре. Устанавливается из ядра
по SSH: «Настройки → Агенты → установить» (проверка ОС/компонентов/репозиториев,
установка недостающего, деплой скрипта, cron `*/5 * * * *`, тестовый запуск).

### Поведение агента (cron каждые 5 минут)
1. **Конфиг с ядра**: перед запуском агент забирает конфиг с ядра
   (`GET /api/agent/config` по X-Agent-Key): список сетей, poll_file.
   **Любое изменение настроек агента в ядре (сети, poll_file) автоматически
   прилетает на агента** на ближайшем cron-цикле; копию конфига агент кэширует
   локально (`/etc/ipam_agent.cfg`) на случай недоступности ядра.
2. **Троттлинг**: повторный отчёт не чаще 30 минут (marker-файл mtime),
   кроме принудительного опроса.
3. **Принудительный опрос из ядра**: «Настройки → Агенты → принудительный опрос»
   → ядро по SSH (SSH-доступ агента хранится в ядре) трогает файл-триггер
   (по умолчанию `/var/lib/ipam_agent/force_poll`); на ближайшем cron-цикле
   агент видит триггер, сканирует немедленно и удаляет триггер.
4. **Сканирование**: nmap -sn (MAC + vendor) или ARP-таблица (MAC) — по наличию nmap;
   троттлинг cron'а (5 мин) + внутренний троттлинг (30 мин) = до 12 отчётов/час,
   фактически — по расписанию ядра.
5. **Отчёт**: `POST /api/agent/report` (X-Agent-Key), тело
   `{"hosts": [{"ip","mac"?,"vendor"?}]}`; отчётный файл-маркер мtime.

### Связь
- Агент → ядро: только один исходящий HTTPS (самоподписанный ядра: `-k` или
  `IPAM_CA_FILE=/путь/ipam.crt` для честной проверки сертификата).
- Ядро → агент: только принудительный опрос по SSH (хранящийся SSH-доступ агента).
- Входящих портов на агенте нет вообще.

### Надёжность
- Агент без состояния: заменяется за минуты (переподнять скрипт = «установить»).
- Отключение агента в ядре → конфиг отдаёт 403, отчёты отклоняются.
- `last_report_at` в карточке агента в ядре — свежесть отчётов.

## 10. Решения (принято 2026-08-18)

1. Авто-скан **по расписанию** с первого этапа (интервал на сеть) + ручной запуск.
2. **Несколько пользователей**: JWT, роли admin/operator/viewer, audit log изменений.
3. Алерты **пока только в UI** (лента событий + бейджи); вебхук (Telegram/Slack) — опция позже.
4. Frontend: **React + ECharts**.

Дальше: прототип UI (грид + график) → каркас проекта (MVP, ~1–1.5 нед).
