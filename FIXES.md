# Исправления по результатам аудита

Ниже — 4 замечания аудита и как они реализованы **в реальном коде** (примеры «до/после»
из отчёта были написаны по упрощённому псевдокоду и адаптированы под фактическую
архитектуру: `create_subnet` живёт в роутере, `dns.py` опрашивает серверы поодиночке
со статистикой, в `docs.py` не было и allowlist-а).

---

## 1. Race condition при проверке пересечения CIDR

**Проблема:** `check_overlap()` выполнялся в Python-коде, проверка и вставка —
двумя шагами; два конкурентных запроса могли одновременно пройти проверку.

**Решение** (`backend/app/service.py`, `backend/app/routers/subnets.py`,
`backend/app/routers/phpipam.py`):

* `subnet_write_lock()` — критическая секция «проверка пересечения + вставка +
  материализация + commit»: `create_subnet()` и импорт phpIPAM выполняются под ним;
* внутри процесса — `asyncio.Lock`; между воркерами/процессами на PostgreSQL —
  `pg_advisory_xact_lock` (снимается на commit/rollback);
* для SQLite межпроцессную сериализацию даёт собственная блокировка записи SQLite.

**Почему не exclusion constraint:** вложение подсетей в master-сети — заявленная
функция («как в phpIPAM»), а `EXCLUDE USING gist (cidr inet_ops WITH &&)` запрещал бы
любое пересечение, включая вложение. Бонус: два корректных CIDR-префикса физически
не могут «частично пересекаться» (они либо вложены, либо дизъюнктны), поэтому лок +
уникальность `cidr` полностью закрывают задачу. Тест: 3 конкурентных создания одного
CIDR → ровно один успех, остальные 409.

## 2. Материализация полной таблицы IP для крупных сетей

**Проблема:** для каждого адреса сети создавалась строка `ip`: /16 → 65 534 строки,
/8 → 16 млн (импорт phpIPAM не проходил валидацию /16 и мог принести такую сеть).
В коде уже была пометка «для больших — разреженный режим, не реализован».

**Решение** (`service.py`, `models.py`, `db.py`, `scanner/engine.py`, `routers/*`, `seed.py`):

* `Subnet.sparse` (флаг) + миграция БД (PostgreSQL и SQLite);
* `is_sparse(cidr)`: сети **шире /20** (prefixlen < 20) не материализуются — хранятся
  только реально известные адреса (шлюз, reserved/used, живые после скана);
* «свободно» вычисляется динамически: `total = ёмкость CIDR`,
  `free = total − used − reserved − cond_free` (общие правила «offline < 3 дн. —
  усл. освобождён» сохранены) — в `usage_counts`, `finish_counts`,
  `finish_subnet_counts`, `/overview`, `/subnets`, `/usage`;
* сканер создаёт строки для живых адресов без них (не трогая адреса вложенных сетей);
* `PUT /api/ips/{ip}` создаёт строку при первом изменении свободного адреса
  (раньше требовалась заранее материализованная строка — иначе резерв был невозможен);
* `/subnets/{id}/blocks` для sparse считает ёмкость каждого блока и выдаёт **все**
  блоки сети; `UsageSnapshot.total` — ёмкость сети.

Плотные сети ≤ /20 (до 4094 строк) и поведение существующих БД не меняются.

**Попутно исправлены два латентных бага блоков /24** (замечались при реализации):
`ip_network(base, block_bits)` создавал `/32` вместо `/24` (drill-down блока фильтровал
по одному IP), а `min(24, prefixlen)` вместо `max(24, prefixlen)` сводил крупную сеть
в один блок.

## 3. Нет retry-логики для DNS-запросов (PTR)

**Проблема:** одиночный запрос к DNS без повторов; при временной недоступности
hostname не определялся.

**Решение** (`backend/app/scanner/dns.py`):

* на каждый `(IP, сервер)` — до `retries + 1` попыток (по умолчанию 2 повтора)
  с экспоненциальной задержкой 0.5 с, 1 с;
* повторяются **только** таймауты и сетевые ошибки; окончательные ответы
  (NXDOMAIN / NOERROR без записи / REFUSED / SERVFAIL) не повторяются —
  сразу переход к следующему серверу;
* в статистику «Лога сканера» добавлен счётчик `retries` (виден в UI);
* семантика «сервер ответил / не ответил» и fallback на системный резолвер
  (`socket.gethostbyaddr`, видит /etc/hosts) сохранены.

## 4. Загрузка файлов без проверки содержимого (magic bytes)

**Проблема:** тип файла доверял заголовку `Content-Type` (в `docs.py` не было даже
allowlist-а); исполняемый файл с поддельным типом проходил. Максимальный размер
(`DOCS_MAX_UPLOAD_MB`) уже контролировался.

**Решение** (`backend/app/routers/docs.py`, `requirements.txt`, `Dockerfile`):

* allowlist MIME (документы, изображения, архивы/офис-контейнеры, `text/*`, скрипты
  как исходный текст — они правятся в редакторе UI);
* определение реального типа: `python-magic` (libmagic; в Docker добавлен `libmagic1`),
  без него — встроенный детектор по сигнатурам + текстовая эвристика;
* исполняемый код (ELF / PE / Mach-O / Java class) запрещён **всегда** — по сырой
  сигнатуре, независимо от Content-Type;
* заявленный и фактический тип должны быть в allowlist и совпадать по классу
  (PDF с сигнатурой PNG, «текстовая» ELF-болванка и т.п. отклоняются);
* сигнатурная проверка `%PDF`/PNG/JPEG/GIF/WebP/ZIP/GZIP, SVG — по `<svg>`;
* сохраняется нормализованный MIME (фактический не противоречит заявленному);
* при выдаче файла: `X-Content-Type-Options: nosniff`; активный контент
  (HTML/SVG/XML/JS) — всегда `attachment` (защита от stored XSS).

## 5. (баг) При импорте phpIPAM разные VLAN сливались в один

**Проблема:** много сетей после импорта оказывались в одном VLAN. Причина — правило
слияния в `backend/app/routers/phpipam.py`: запись phpIPAM считалась дублем по
**одному** признаку — «имя занято **ИЛИ** номер занят» (`is_dup = name || vid`) — и
молча привязывалась к уже созданному VLAN (`our_vlans[name].id`). Типичные данные
phpIPAM, где это ломается: одинаковые имена VLAN в разных секциях/филиалах («Users»
№10 и «Users» №20) и одинаковые номера в разных L2-доменах (`vlans.domainId`).
Слияния происходили молча — в отчёте импорта не было ни одного предупреждения.

**Решение** (сверено с `db/SCHEMA.sql` phpIPAM: `subnets.vlanId` → внутренний PK
`vlans.vlanId`, номер 802.1Q — поле `number`):

* сопоставление с ядром — **сначала по номеру** (наш `vid` уникален, номер = L2-
  идентичность), при отсутствии номера — по имени;
* **разные номера + одинаковые имена = разные VLAN — НЕ сливаются**: второй
  создаётся с уточнённым именем («Users (20)»), в отчёте — предупреждение;
* совпадающие номера в phpIPAM (L2-домены) — вынужденное слияние (у нас номер
  уникален), но с явным предупреждением «объединены, один номер»;
* каждое слияние и каждое переименование пишется в `issues` отчёта импорта;
* ключи карты `vlan_map` нормализованы к строкам (phpIPAM отдаёт `id`/`vlanId` то
  строками, то числами — рассинхрон типов молча отвязывал VLAN);
* сеть с `vlanId`, отсутствующим в списке VLAN, — предупреждение вместо молчания;
* повторный импорт идемпотентен (новые VLAN не плодятся).

### Прозрачность: «почему сеть попала в этот VLAN»
Отчёт импорта (`check`/`apply`) теперь содержит:
- `vlans_report` — по каждой записи VLAN phpIPAM: что сделано (использован существующий / объединён по номеру / создан / создан с переименованием при занятом имени);
- `vlan_links` — по каждой сети: привязка из phpIPAM (`«Имя» №number id=NN`) и итоговое наше VLAN.

Правило привязки (жёсткое): **VLAN берётся ТОЛЬКО из поля `vlanId` сети** (`subnets.vlanId` → запись `vlans` в phpIPAM). Описания и имена сетей/секций НИКОГДА не парсятся на предмет упоминаний VLAN. Сеть без привязки (`vlanId` отсутствует, `0` или `None`) — всегда «без VLAN»; общей ловушки для пустого ключа нет. Если `vlanId` — не id записи, а номер 802.1Q (смешанные данные), сопоставление идёт по номеру с пометкой в issues; битая запись VLAN без id не создаёт «фантомный» VLAN.

Возможные причины «много сетей в одном VLAN»: (а) в phpIPAM все сети действительно привязаны к одной записи — импорт честен; (б) прежнее слияние по имени/номеру — исправлено §5; (в) catch-all пустого ключа — исправлено здесь. Ответ для конкретного набора данных даёт таблица «VLAN у сетей» в предпросмотре.

### Режим перепривязки VLAN существующих сетей (`relink_vlans`)
По умолчанию импорт НЕ трогает `vlan_id` уже существующих сетей (обновляются только
имя/описание) — поэтому исправление привязок в phpIPAM само по себе не меняло ядро.
Флаг `relink_vlans` (чекбокс «VLAN существующих → перепривязать к привязке phpIPAM»)
приводит `vlan_id` существующих сетей к привязке из phpIPAM, включая отвязывание
(`vlanId=0` → «без VLAN»). В предпросмотре колонка «в ядре» таблицы «VLAN у сетей»
показывает переход «старое → новое», счётчик — «Сети: перепривязка VLAN».
Без флага колонка «в ядре» показывает факт из БД (что реально привязано сейчас).

### Дубли номера VLAN в phpIPAM (разные L2-домены / оборудование)
Если в phpIPAM несколько записей VLAN с одним номером 802.1Q (типично: один номер на разных
устройствах / L2-доменах — в карточках сетей они выглядят одинаково, «10 (Vlan 10)»), в ядре они
неизбежно объединяются в один VLAN: номер в ядре уникален (`vlans.vid` UNIQUE). Импорт теперь
объясняет это явно: issue «VLAN №N: в phpIPAM K записи с этим номером: …» перечисляет записи
с id и доменами, а подписи записей в таблицах «VLAN: phpIPAM → ядро» и «VLAN у сетей» включают
id и L2-домен. Лечение: различить записи в источнике (разные номера или имена); если номера
обязаны остаться одинаковыми (реально один тег на разных устройствах) — потребуется поддержка
L2-доменов в ядре (отдельная фича). После правки источника: предпросмотр с чекбоксом
`relink_vlans` покажет переходы «старое → новое» по каждой сети.

### Очистка БД не удаляет документацию (статьи)
`POST /api/admin/clear-db` раньше стирал всё, включая разделы/страницы документации
и файлы на диске. Теперь очистка затрагивает только операционные данные
(IP, сети, VLAN, агенты, сканы, события); пользователи, настройки и ВСЯ документация
(разделы, статьи, прикреплённые файлы) сохраняются. Текст подтверждения в UI
обновлён соответственно; проверка — smoke_test.py сценарий 8.

### Точность сопоставления VLAN: номер + имя + описание
Подписи записей phpIPAM в отчёте («VLAN: phpIPAM → ядро», «VLAN у сетей», issue про дубли
номера) включают поле **description** записи — по нему различимы записи-близнецы вида
«10 (Vlan 10)» с разных устройств. При сопоставлении по номеру: если имя и номер совпали,
а описания записи phpIPAM и VLAN ядра различаются — выдаётся явный issue («возможно, это
VLAN на другом оборудовании; в ядре объединено по номеру»). Описание записи при создании
VLAN сохраняется в `vlans.descr`, поэтому сравнение работает и на повторных импортах.

### Вложения Документации переживают пересборку контейнера
Механизм потери: без `DOCS_DIR` файлы писались в `/app/docs_files` — внутрь слоя образа,
и гибли при пересборке (`COPY backend/app ./app`). Защита в четыре слоя:
1. **Dockerfile**: `ENV DOCS_DIR=/docs` + `VOLUME /docs` — даже без compose/старого compose-файла
   вложения идут в том (anonymous), а не в слой образа;
2. **docker-entrypoint.sh**: `mkdir -p $DOCS_DIR`, громкое предупреждение, если `DOCS_DIR`
   указывает внутрь `/app`, печать каталога и числа файлов при старте, и спасение файлов
   из старого `/app/docs_files` (`cp -an`, без перезаписи);
3. **compose-файлы**: именованные тома `ipam_docs` / `ipam1_docs` / `ipam2_docs` (уже были);
4. **lifespan main.py**: проверка целостности при старте — если строк DocFile больше, чем
   файлов на диске, в лог пишется ERROR со списком (до 5 имён) и каталогом DOCS_DIR.
Убивают том только `docker compose down -v` и `docker volume prune` — не используйте их
без бэкапа: `docker run --rm -v ipam_docs:/d -v $PWD:/b alpine tar czf /b/docs.tgz -C /d .`

### deploy.sh (боевой скрипт деплоя, в репозитории)
Помимо бэкапа тома вложений перед `up` и grep-проверок compose (том `docs:/docs`
и `DOCS_DIR: /docs`, комментарии игнорируются), скрипт спасает файлы из старого
внутриобразного каталога `/app/docs_files`: до `up` делает `docker cp` старого
контейнера в `backup/rescue_<org>`, после `up` переносит их в `/docs` нового
контейнера без перезаписи существующих. Контроль после up: том существует и число
файлов в `/docs`. Финальный `docker ps` фильтрует по label compose-сервиса, а не
по имени каталога.
